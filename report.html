1. Claude가 광고 준비를 맡아 반복 입력과 확인 부담을 줄이는 것을 목표로 합니다

광고마다 자료를 찾고, 설정을 입력하고, 제대로 반영됐는지 확인하는 일이 반복됩니다. Claude가 자료 확인부터 광고 준비와 설정 대조까지 맡고, 담당자는 판단이 필요한 내용을 확인한 뒤 준비된 광고를 최종 검토하고 직접 게시하거나 명시적으로 게시를 지시하는 흐름을 제안합니다.

같은 내용을 반복 확인하고 작업을 계속 지켜보는 부담을 줄이는 것이 목표입니다

담당자가 세팅 과정 내내 붙어 있기보다, 필요한 판단과 마지막 확인에 집중할 수 있게 하는 것이 목표입니다. D2 결정 전 제안에서는 영상 내용 검수를 필요한 경우 별도로 요청하고, 광고에 소재·문구·링크·예산이 맞게 들어갔는지 확인하는 기본 검수는 유지합니다. 직접 게시 또는 명시적 선택 게시한 광고의 실제 상태가 확인되면 Slack에 자동으로 공유하도록 개발합니다.

2. 최종 확인 후 직접 게시하거나 선택 게시를 지시합니다

아래는 개발할 흐름입니다. 영상 검수를 요청하지 않아도 기본 광고 준비는 진행하며, 영상 검수 미실행은 결과에 그대로 표시합니다.

자료 확인 Claude가 기존 요청·자료를 읽고 브랜드·캠페인별로 나눕니다. 부족하거나 충돌하는 내용만 질문합니다.

기본 설정 대조 실제 반영된 설정과 요청을 비교합니다. 명확한 입력 오류는 허용 범위에서 수정·재확인하고, 판단이 필요한 건은 담당자에게 보여줍니다.
최종 확인·게시 담당자가 모든 광고의 상태와 근거를 확인한 뒤 직접 게시합니다. 또는 확인한 광고 ID와 설정 버전으로 명시적 게시를 지시할 수 있습니다.
게시 후 공유 게시 확인 기능이 실제 결과를 확인한 광고만 지정 Slack 채널로 자동 공유합니다. 심사 중·실제 노출 여부는 구분합니다.

설정 대조는 기본으로, 영상 검수는 요청 시 실행하는 안을 제안합니다

대상 매체는 Meta·Google·TikTok입니다. 복수 브랜드 요청과 Slack 자동 공유는 2358works 제안이며 설문 전원의 합의로 해석하지 않습니다.

최종 확인한 광고만 명시적으로 게시할 수 있습니다

직접 게시를 기본으로 유지하면서 선택 게시를 이번 납품 기능에 포함합니다. 예를 들어 “ad-publish: 내가 최종 확인한 설정 버전 v3의 광고 A·B만 게시해 주세요”라고 요청합니다. 일반 승인·준비 요청은 게시 지시가 아닙니다. 실제 스킬명은 2주차에 확정합니다.

실행 계층은 게시 권한, 승인한 설정 버전, 지정 광고 ID와 현재 실제값을 대조합니다. 설정이 바뀌면 재확인하고, 중복 지시는 기존 결과를 반환합니다. 응답 유실은 먼저 실제 상태를 조회하며 불확실하면 보류합니다. 일부 실패는 광고별로 나눠 안내하고, 성공한 광고를 다시 게시하거나 기존 운영 광고를 자동 변경·중지·삭제하지 않습니다. 게시 확인분만 Slack에 공유하며 심사·노출은 별도로 표시합니다.

사용자는 선택 게시를 사용하지 않아도 됩니다. 다만 납품 기능이므로 승인 불일치·설정 변경·중복 지시·응답 유실·부분 실패 시험은 필수입니다(PRD SK09·VT19). 총 6주·세 매체 범위는 유지하며, 추가 공수나 외부 승인 영향은 아직 해결됐다고 볼 수 없습니다. 실제 게시 시험은 계정·대상·예산·기간 승인 후 수행하며 현재 미실행입니다.

새 브랜드도 기존 Notion 브랜드 DB에서 읽습니다

위캐리는 지금처럼 기존 Notion 브랜드 DB에 신규 브랜드를 추가합니다. 자동화용 브랜드를 다시 등록하거나 별도 등록 스킬을 실행할 필요는 없습니다. 광고 준비 요청이 들어오면 시스템이 해당 브랜드와 연결된 제품·자료·운영 기준을 읽도록 개발합니다.

기존 자료에 계정·문구·링크·예산·사용할 소재가 있으면 재사용합니다. 필요한 값이 없거나 서로 다를 때만 기존 업무 담당자에게 확인합니다. 새 광고 계정이나 자료에 접근할 권한이 없으면 2358works가 필요한 연결을 안내하고 계정 소유자가 권한을 부여합니다. 브랜드별 코드를 새로 만들거나 같은 정보를 다시 입력하는 절차를 기본으로 요구하지 않습니다.

위캐리가 평소처럼 브랜드·제품·소재 링크를 Notion에 등록한 뒤 “이 업로드 요청으로 광고를 준비해줘”라고 요청합니다. 시스템은 연결된 브랜드 DB와 자료를 읽습니다.

상황 처리 방법
필요한 정보와 권한이 준비됨 기존 자료를 읽어 광고 준비 진행
이번 광고의 예산·최종 문구 등 일부 값이 없음 없는 값만 모아서 기존 담당자에게 질문
새 광고 계정·Drive 자료에 접근할 수 없음 개발팀이 필요한 연결을 안내하고 소유자가 권한 부여
새로운 매체·광고 유형을 사용함 개발팀이 지원 여부를 시험하고 결과 안내

요청 예시: “ad-prepare: Notion에 추가한 브랜드 A의 이 [업로드 요청 링크]로 광고를 준비해줘. 필요한 값이 없으면 모아서 알려줘.”

브랜드 DB 항목 추가는 기존 위캐리 업무이고, 새 항목을 읽어 처리하는 기능은 개발팀이 제공합니다. 자동화가 브랜드 DB를 새로 만들거나 변경하는 기능은 기본 범위에 넣지 않습니다.

3. 자동화 업무는 스킬 이름으로 시작하는 방식을 제안합니다

스킬은 ‘광고 준비’처럼 자주 하는 업무의 절차를 묶어 둔 것입니다. 두 방식 모두 같은 실행 기능과 같은 브랜드 규칙을 사용합니다. 달라지는 것은 요청을 시작하는 방식입니다.

아래는 같은 실무를 두 방식으로 요청한 제안 예시입니다. ad-prepare(광고 준비), video-review(영상 검수), result-status(결과 조회), ad-publish(선택 게시)는 설명용 영어 스킬 이름이며 최종 이름과 호출 표기는 T8에 따라 2주차 말 정합니다. 실제 처리 결과나 고객 원문은 아닙니다.

같은 업무 스킬 이름으로 시작하는 예시 — 권장안(D1 결정 전) 자연어 요청 예시
광고 준비 “ad-prepare: 이 요청 링크와 자료로 비활성 광고를 준비하고 실제 설정을 대조해 주세요.” “이 요청 링크와 자료에 맞춰 광고를 게시하지 않은 상태로 준비하고 실제 설정을 대조해 주세요.”
선택 영상 검수 “video-review: 기존 플랫폼에 올라간 이 영상들에서 검은 화면과 자막 문제를 확인해 주세요.” “기존 플랫폼에 올라간 이 영상들에서 검은 화면과 자막 문제를 확인해 주세요. 광고 준비와 별도로 요청합니다.”
선택 게시 “ad-publish: 최종 확인한 설정 버전 v3의 광고 A·B만 게시해 주세요.” “내가 최종 확인한 설정 버전 v3의 광고 A·B만 게시해 주세요.”
결과 조회 “result-status: 이 작업의 준비·보류·게시 확인·공유 상태와 제가 확인할 내용을 보여 주세요.” “이 작업의 준비·보류·게시 확인·공유 상태와 제가 확인할 내용을 보여 주세요.”

실행하는 기능은 같습니다. 업무를 요청하는 방식만 정하면 됩니다.

방식 좋은 점 주의할 점
자연어 이름을 몰라도 원하는 일을 설명할 수 있고 상황을 덧붙이기 쉬움 “이것 처리해 줘”처럼 범위가 모호하면 확인 질문이 필요
스킬 이름 반복 업무의 시작점을 짧게 지정하고 팀에서 같은 절차를 찾기 쉬움 이름과 기능을 처음에는 알아야 하며, 이름만으로 대상·자료가 정해지지는 않음

AI가 익숙하지 않은 담당자에게는 업무별 스킬 이름을 보여주고 그 이름으로 시작하는 방식을 권장합니다. 정해진 절차가 필요한 자료와 확인할 항목을 순서대로 안내하면 요청·확인 누락을 줄이는 데 도움이 될 수 있습니다. 신규 입사자도 같은 절차와 안내를 사용해 일관된 업무 매뉴얼로 활용할 수 있습니다. 이는 설계상 기대효과이며, 누락 감소나 교육 효과를 실측하거나 보장한 결과는 아닙니다.

자연어 요청도 함께 지원하는 방향입니다. 스킬 이름을 모르거나 상황을 설명하고 싶을 때는 평소 말하듯 요청하면 됩니다. 두 방식의 기능·검사 범위·게시 권한은 같고 요청을 시작하는 방법만 다릅니다. 미팅에서는 스킬 이름으로 시작하도록 안내하는 권장안이 실제 담당자에게 편한지 확인합니다.

처음에는 “지금 할 수 있는 업무를 알려 주세요”, “광고 준비와 영상 검수는 무엇이 다른가요?”, “이 작업에는 어떤 스킬이 필요한가요?”라고 질문해 찾을 수 있도록 합니다. 용어집·업무별 예시·현재 단계 안내를 함께 제공하면 이름을 외우는 부담과 동료에게 반복 질문하는 일을 줄일 수 있습니다. Q20은 현장 설명을 통한 교육 4/4, Q21은 자료 위치 공란 4/4이므로 가이드가 없다고 단정하지 않고 기존 교육에 보탤 방식을 제안합니다.

Claude는 요청을 받고, 실행 계층이 광고 준비를 이어갑니다

Claude Team과 기존 업무 환경을 우선 활용하며, 실행 계층은 작업을 처리하는 기능 구분입니다. 별도 유료 서버를 기본 요구로 두지 않습니다.

담당자는 Claude에서 ad-prepare와 기존 Notion 요청 링크로 시작합니다. Claude가 필요한 내용을 정리하면 실행 계층이 Notion의 확정 문구·링크·예산과 Drive 소재를 읽고 광고를 중지 상태로 준비합니다. 담당자는 전체 결과와 요청에서 달라진 부분을 확인한 뒤 직접 게시하거나 지정 광고의 게시를 명시적으로 지시합니다.

대화가 끝나도 작업 기록은 실행 저장소에 남도록 개발합니다. 일부 광고에서 문제가 생기면 정상 광고는 유지하고 필요한 항목만 확인합니다. 게시 후에는 실제 확인된 상태를 Slack에 공유합니다. D2 결정 전 제안에서는 영상 내용 검수를 별도로 요청할 때만 실행합니다.

이 흐름은 개발할 구조입니다. Google 테스트 계정·Meta 새 일반 계정의 시험 유형·항목에 한해 개별 API 생성·조회를 확인했으며, 고객 계정 권한과 세 도구의 전체 연동·복구는 개발 진행하면서 최종 검증할 예정입니다.

4. 시스템이 업무 단계별로 어떤 자료를 읽는지 설명합니다

Notion과 Drive의 기존 자료를 유지하고, Claude가 작업 단계에 맞는 자료를 읽도록 개발합니다. 기존 자료의 위치와 일부 연결 관계는 조사했지만, 승인된 소재부터 실제 광고 설정까지 이어지는 연동은 아직 검증하지 않았습니다. 아래 표와 도식은 실제로 동작 중인 시스템 설명이 아닌 개발 제안입니다.

Notion에서 요청과 규칙을 읽고, Drive 소재로 광고를 준비하는 순서

Claude는 요청·누락 확인을 안내하고 실행 계층이 허용된 자료 조회·광고 준비·실제 설정 대조를 수행하는 구조입니다. 아래 흐름에서 Claude의 작업은 이 실행 계층을 통한 처리를 포함합니다.

단계 시스템(Claude·실행 계층)이 읽을 곳 읽은 정보로 수행할 일
1. 요청 확인 Notion 광고 요청 대상 브랜드·매체·캠페인·요청 수량·일정과 자료 링크를 확인합니다.
2. 브랜드 기준 확인 기존 Notion 브랜드 DB와 연결된 규칙 페이지 계정 참조 정보·담당자·공유 채널과 문구·링크·예산·자동 옵션 규칙을 확인합니다.
3. 소재 연결 요청에 연결된 Drive 소재 폴더와 원본 파일 정보 광고별로 사용할 소재와 버전을 연결합니다. 이름·수정일만으로 승인본을 고르지 않고 승인 근거를 확인합니다. 이 단계의 소재 연결 확인은 영상 내용 검수와 구분합니다.
4. 문구·주소 연결 기획 문서와 링크 시트 광고 입력 문구와 실제 사용할 랜딩·추적 URL을 읽어 각 소재에 연결합니다. 스크립트를 광고 문구로, 일반 URL을 발급된 추적 URL로 임의 대체하지 않습니다.
5. 비활성 광고 준비 광고 플랫폼의 대상 계정·캠페인·현재 설정 연결 도구가 확인된 입력값으로 비활성 광고를 준비합니다. 게시·노출되지 않는 상태를 보장할 수 없으면 자동 준비를 보류합니다.
6. 실제 설정 대조 준비된 광고의 실제 설정과 앞 단계의 요청·규칙·소재·문구·URL 입력 계획과 실제 반영값을 비교하고 일치·불일치·미확인 및 담당자가 판단할 내용을 보여줍니다.
7. 담당자 게시 후 공유 직접 게시 또는 명시적 선택 게시한 광고의 매체 상태와 합의한 Slack 채널 정보 게시 결과가 확인된 광고만 Slack에 공유합니다. 게시·심사·실제 노출 상태는 구분합니다.

작업 상태는 실행 계층에 저장합니다. 기존 Notion에 업무 결과를 자동 기록할 필요가 있으면 기록할 항목만 확인합니다. Notion에는 요청·브랜드별 규칙·판단 근거를, Drive에는 소재와 문서 원본을 두고, Slack에는 확인된 게시 결과를 공유하는 구조를 제안합니다. 브랜드 정보는 기존 Notion 브랜드 DB를 읽습니다. 새 DB·속성 추가는 기본 전제가 아니며 실제 필요할 때만 변경 내용을 설명합니다. Slack 공유 성공만으로 Notion 기록까지 끝났다고 표시하지 않습니다.

자료가 있더라도 이번 광고에 사용할 수 있는지는 별도 확인합니다. 제작 완료와 사용 승인·게시를 구분하고, 자료 간 충돌은 두 출처와 영향 광고를 모아 질문합니다. 접근 실패는 자료 없음으로 바꾸지 않습니다. 고객 보고서에는 원문 계정·개인정보·민감한 파일 내용 대신 필요한 근거만 요약합니다.

예시 | Claude는 어떤 자료를 읽고 광고를 준비하나요?

담당자가 기존 Notion 업로드 요청 링크를 전달하면, Claude가 연결된 브랜드 정보·운영표·소재 폴더를 읽어 비활성 광고를 준비하도록 개발합니다. 기존 자료에서 확인되는 값은 다시 입력하지 않는 방향입니다. 이번 광고에 쓸 값이나 사용 승인 여부를 알 수 없을 때만 기존 담당자에게 확인합니다. 별도 입력 양식을 전제로 하지 않습니다. 아래는 전달받은 실제 자료 조사 내용을 바탕으로 구성한 개발 예정 흐름입니다. 자료의 존재와 일부 연결 관계는 확인했지만, 자동화 구현·실계정 실행 검증이 완료된 것은 아닙니다. 브랜드명과 내부 주소는 역할명으로 바꿨습니다.

출처 위치 Claude가 참고할 내용 담당자가 확정할 사항
① Notion 업로드 요청 제품·매체·소재명·수량·파일 경로·담당자와 이번 요청 내용 이번에 준비할 광고의 대상과 범위. 본문이 비어 있으면 연결 자료에서 먼저 찾고 부족한 정보만 확인
② Notion 브랜드 페이지·제품 DB 담당마케터·제품 관계·Drive·운영표·광고 관리자 링크 대상 브랜드와 제품, 사용할 계정이 맞는지 확인
③ 운영표·회의록 해당 작업·매체·일정과 기존 광고를 찾을 단서 이번 요청에 적용할 기준. 과거 운영값을 이번 요청의 확정값으로 자동 대체하지 않음
④ Drive 소재 폴더 파일 ID와 A1~A4 같은 파일 번호, 자막·클린 등 버전과 용도 사용할 최종 파일과 매체별 버전. 폴더 안의 모든 파일을 자동으로 등록하지 않음
⑤ 제품별 링크 모음 일반 랜딩·비밀 랜딩 후보와 제품별 주소 각 광고에 사용할 최종 링크와 추적값. 요청한 세트의 링크가 없다고 단품 링크로 대체하지 않음
⑥ 기존 자료에서 모은 이번 광고의 입력값 기존 요청·운영표·기획 자료의 계정·매체·문구·예산·기간·랜딩/추적값을 연결 이미 있는 값은 재입력하지 않음. 빠지거나 충돌하는 값만 질문하며 자동화용 새 입력 양식은 요구하지 않음
⑦ 광고 매체 계정 접근 권한·지원 유형과 준비된 광고의 실제 설정 Claude가 비활성으로 준비한 결과를 요청값과 비교한 뒤, 담당자가 최종 확인한 뒤 직접 게시 또는 명시적 선택 게시 지시

예를 들어 요청 수량이 6개인데 폴더에 영상 8개와 작업용 폴더가 있다면, Claude가 8개를 모두 등록하는 방식이 아닙니다. 자막·클린 등 버전과 요청의 관계를 먼저 찾고, 어떤 6개를 어느 매체에 사용할지 불명확한 부분만 담당자에게 확인하도록 합니다. 이는 조사에서 확인한 수량 차이를 비식별화한 설명이며, 자동 처리에 성공한 사례는 아닙니다.

파일명·수정일·폴더 수량 일치만 있으면 후보입니다. 승인자 역할·승인 기록·대상 파일/문구 버전이 요청에 연결되어야 승인 근거가 있는 자료로 취급합니다. 해결되지 않은 모호성만 요청별로 묶어 질문하고, 답변·확정 시각·결정 역할을 request_revision과 입력 스냅샷에 연결합니다. 파일·문구·권한 변경 시 영향 항목만 stale 처리하고 재확인하며 정상 항목은 보존합니다. 403·404는 접근 실패 기록이고 삭제 증거가 아닙니다.

기대효과와 확인 방법

광고 자료를 찾고 같은 값을 반복 입력하거나, 작업이 끝날 때까지 계속 확인하는 부담을 줄이는 것이 목표입니다. 실제로 얼마나 편해지는지는 개발 후 위캐리 업무에 사용해 보면서 확인합니다.

기대효과 사용하면서 확인할 내용
자료를 찾고 연결하는 부담 감소 요청에 맞는 소재·문구·링크가 연결되는지, 담당자가 다시 찾아야 하는 자료는 무엇인지
다수 광고 일괄 준비 한 요청의 여러 광고가 각 소재·설정에 맞게 준비되는지
설정 오류에 대한 불안 감소 실제값·차이·미확인 표시가 최종 판단에 도움이 되는지
반복 입력과 재확인 감소 같은 값을 다시 입력하거나 같은 질문에 답하는 일이 줄었는지
작업을 계속 지켜보는 부담 감소 문제가 생겼을 때 필요한 내용만 안내받고, 중단된 작업을 이어갈 수 있는지
처음 사용하는 담당자도 쉽게 업무 진행 업무 요청·결과 확인·새 브랜드 자료 확인·문제 대응을 직접 할 수 있는지

개발 완료 여부는 약속한 기능이 제대로 작동하고 담당자가 핵심 사용 방법을 익혔는지로 확인합니다. 기능 시험이나 필수 실습이 끝나지 않으면 완료로 표시하지 않습니다. 구체적인 시험 기준은 PRD에 정리합니다.

기대효과는 아직 확인된 성과가 아닙니다. 사용 후 효과가 충분히 확인되지 않았다는 이유만으로 기능 개발이 미완료인 것으로 판단하지는 않습니다. 작업시간을 얼마나 줄일지는 별도 목표로 약속하지 않으며, 다른 회사의 사례를 위캐리의 예상 성과로 제시하지 않습니다.

8. 다음 단계는 개발, 실제 업무 QC, AX교육입니다

기본 일정은 1~2주 분석·협의, 3~4주 개발, 5주 검증·보완, 6주 교육·최종 확인입니다. 개발·보완이 최대 1주 더 필요하면 교육 기간을 줄여 총 6주 안에서 조정합니다. 완료된 기능부터 검증을 병행하고 4주차 중간 시연과 6주차 최종 확인은 유지합니다. 보완 시 5주차 개발 보완과 완료 기능 검증을 병행하고, 6주 초 잔여 QC·재확인 후 6주 후반에 축소 교육·최종 확인을 진행합니다. 교육 기간이 줄어도 업무 요청·결과 확인·신규 브랜드 자료 확인·문제 대응의 핵심 실습은 유지합니다. 일정 도달만으로 필수 시험을 통과 처리하지 않습니다. 실제 날짜는 양측이 기록한 시작일 기준으로 정합니다.

업무 분석·요구사항 협의에서 처리할 업무와 운영 방식을 정한 뒤 기능 개발·연동을 진행합니다. 주요 기능 중간 시연에서는 요청부터 준비 결과 확인까지의 흐름을 함께 확인합니다.

완료된 기능부터 개발과 병행해 실제 업무의 정상 사례와 누락·충돌·부분 실패 같은 예외 사례로 QC를 진행합니다. 확인된 오류를 보완하고 다시 확인하며, 시험 전에는 실제 광고 게시·공유의 허용 범위를 별도로 정합니다.

AX 교육에서는 스킬로 업무 요청하기, 결과와 미확인 항목 확인하기, 기존 DB의 신규 브랜드 자료 확인하기, 문제 발생 시 조치·지원 요청하기를 직접 연습합니다. 핵심 실습·필수 기능 시험과 운영 준비 조건을 충족하면 운영 전환을 판단합니다. 이 일정은 구현·QC·교육 완료를 의미하지 않습니다.

효과는 반복 확인·중간 개입·입력 오류·재처리·체감 부담이 줄었는지로 확인합니다. 처음 쓰는 담당자가 용어를 질문하고 적절한 업무를 찾아 요청할 수 있는지도 살펴봅니다. Q42의 개인 희망인 ‘시간 절반’을 공동 목표나 달성값으로 쓰지 않습니다.

9. 자주 묻는 질문

스킬 이름을 외워야 하나요?
외우지 않아도 됩니다. 구축 후에는 Claude에게 언제든 “사용할 수 있는 스킬을 알려줘”, “이 스킬은 어떻게 써?”라고 물어볼 수 있도록 합니다. 이름 목록과 사용 예시를 보고 시작하거나 평소 말하듯 요청하면 됩니다.
영상 검수는 매번 해야 하나요?
고객 합의 전 제안은 필요할 때 따로 요청하는 방식입니다. Q36의 자동 검사 선호와 함께 D2에서 결정합니다. 요청하지 않은 영상은 “내용을 확인하지 않음”으로 표시합니다. 그래도 광고에 맞는 소재·문구·링크·예산이 들어갔는지는 확인하고, 담당자가 모든 광고를 살펴본 뒤 게시합니다.
누가 마지막으로 확인하나요?
현재 광고를 세팅하는 담당자가 모든 광고를 최종 확인하고 광고 관리자에서 직접 게시하는 방식을 권장합니다. 최종 확인한 광고 ID와 설정 버전을 지정해 Claude에게 명시적으로 게시를 지시하는 선택 기능도 이번 납품에 포함합니다. 기본은 담당자 직접 게시이며, 명시적 지시 없이 자동으로 켜지 않습니다.
영상이 많으면 비용이 많이 드나요?
개수뿐 아니라 길이·검사 범위·접근 방식에 따라 달라질 수 있습니다. Claude Team을 우선 활용하며 실행 전 검사 범위와 사용량을 안내합니다. 추가 인프라가 실제 필요하면 이유·비용·소유·운영 주체를 제시하고 사용 전에 합의합니다. 원본 후보 20개 중 영상 1개를 읽고 분석용 이미지를 뽑는 전처리만 성공했으며, Claude 내용 시험과 비용 확인, 5·20개 시험은 아직 하지 않았습니다.
자료가 빠졌거나 서로 다르면요?
Claude가 기존 자료에서 먼저 찾아보고, 그래도 알 수 없거나 자료마다 내용이 다르면 담당자에게 묻도록 합니다. 꼭 필요한 정보가 빠진 광고는 기다리고, 필요한 정보가 모두 있는 다른 광고는 계속 준비합니다.
브랜드 규칙이 바뀌면요?
어떤 브랜드에 언제부터 적용할 규칙인지 확인하고, 아직 게시하지 않은 광고 중 해당하는 광고를 다시 확인하도록 합니다. 이미 운영 중인 광고를 자동으로 바꾸지는 않습니다.
게시 전에 팀장 승인이 필요한가요?
담당자 직접 게시를 기본으로 유지하고 명시적 선택 게시도 지원하도록 개발합니다. 담당자 판단으로 게시하는지, 팀장 승인 후 담당자가 게시하는지는 기존 위캐리 절차를 확인해 정합니다. 승인 표현만으로 Claude가 광고를 켜지는 않습니다.
일부만 실패하면 처음부터 다시 하나요?
잘 준비된 광고는 그대로 두고 문제가 생긴 광고만 다시 확인합니다. 광고가 만들어졌는지 알 수 없을 때는 광고 관리자에서 먼저 찾아본 뒤 필요한 작업만 다시 합니다.
Notion과 Slack은 각각 무엇에 쓰나요?
Notion은 자료·판단·진행 기록, Slack은 확인된 게시 결과 공유에 씁니다. 기존 Notion에 결과를 자동 기록할 필요가 있으면 그 항목만 확인합니다.
모든 광고와 영상을 지원하나요?
Google 테스트 계정(Search·Demand Gen 이미지·PMax)과 Meta 새 일반 계정(이미지/트래픽)의 시험 항목에 한해 비활성 생성·재조회를 확인했습니다. TikTok도 위캐리가 사용하는 납품 대상이며, API 연동은 개발 진행하면서 최종 검증 진행 예정입니다. 실제 사용할 고객 계정·광고 유형·영상 지원 범위는 개발 진행하면서 최종 확인합니다.
